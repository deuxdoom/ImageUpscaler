# 처리 방식별 알고리즘 안내

이 문서는 v1.0.0의 실제 구현을 설명한다. 사용 순서는 [README](../README.md)에 있다.
앱 소스와 검증 보고서는 이 배포 안내 저장소에 공개하지 않는다.

## 먼저 고르기

| 화면 이름 | 내부 모드 | 알고리즘 / 가중치 | 어울리는 입력 | GPU | 파일 태그 |
|---|---|---|---|---|---|
| 사진 AI | `Photo` | RRDBNet 23블록 / `realesrgan-x4plus` | 사진·질감이 있는 이미지 | Vulkan | `photo-ai` |
| 이미지 AI | `Illustration` | RRDBNet 6블록 / `realesrgan-x4plus-anime` | 일러스트·아이콘·선화 | Vulkan | `image-ai` |
| 원본 보존 | `Faithful` | 선형 색공간 Lanczos 보간 | 새로운 디테일 추정을 원하지 않는 이미지 | 불필요 | `faithful` |
| 픽셀아트 | `PixelArt` | Nearest neighbor 정수 확대 | 도트·게임 스프라이트 | 불필요 | `pixel-art` |

네 방식 모두 2×·4×·8×를 지원한다. 8×는 별도 알고리즘이 아니라 2× 단계의 결과에 4× 단계를 이어서 적용한다.
AI 두 방식은 사전 학습 모델로 디테일을 추정한다.
원본 보존과 픽셀아트는 학습 모델 없이 계산하며, 작은 글자·정확한 도형은 결과를 직접 비교해 선택한다.

## 공통 처리 순서

```text
입력 헤더 검사 → EXIF 방향·ICC/sRGB 정규화 → RGB/alpha 분리
→ 투명 경계의 RGB 보완 → 선택 방식으로 RGB 확대(8×는 2× 단계 → 4× 단계)
→ AI 단계마다 손상 검사 → alpha를 최종 크기로 한 번 확대·복원
→ 임시 출력 인코딩·크기/alpha 확인 → 중복 없는 이름으로 저장
```

1. `ImageCodec.Inspect`가 단일 프레임, 지원 확장자와 픽셀 수를 검사한다.
   PNG/JPG/WebP/AVIF 외에 BMP/TIFF도 읽는다. 애니메이션·다중 페이지는 거절한다.
2. `ImageCodec.Load`가 EXIF 방향을 적용하고 ICC가 있으면 sRGB로 변환한다.
   출력 계산은 Q8, 즉 채널당 8bit다. 완전히 불투명한 alpha는 제거한다.
3. `AlphaEdges`가 alpha를 보관하고 RGB 입력을 만든다. 세부 절차는 아래 투명도 절을 따른다.
4. `UpscalePipeline`이 모드별 RGB 처리를 2× 또는 4× 단계로 실행한다. 8×는 2× 단계 뒤 4× 단계를 실행한다.
   AI 단계마다 출력이 그 단계 입력의 정확히 가로·세로 4배인지 검사한다.
5. 최종 배율로 RGB와 alpha를 맞춘 뒤 인코딩한다. 원본 EXIF 등의 메타데이터는 제거하고 sRGB 프로필을 넣는다.
6. 출력은 작업 폴더에 먼저 저장한다. 크기와 alpha 유무를 확인한 파일만 결과 폴더에 새 파일로 복사한다.
   이름 충돌은 번호를 붙여 피하고, 복사 실패·취소 시 이번 작업이 만든 부분 파일만 삭제한다.
   원본이나 기존 출력에 덮어쓰지 않으며 완료·오류·취소 후 해당 작업 폴더를 정리한다.


## 사진 AI: Real-ESRGAN x4plus

공식 정의는 RGB 입력/출력 3채널, 특징 64채널, 성장 채널 32, RRDB 23개, 확대율 4다.
이미지 AI의 6블록 모델도 같은 채널 구성을 사용한다.
출처: [Real-ESRGAN 공식 모델 선택 코드](https://github.com/xinntao/Real-ESRGAN/blob/a4abfb2979a7bbff3f69f58f58ae324608821e27/inference_realesrgan.py).

RRDBNet은 첫 3×3 합성곱으로 특징을 만들고 RRDB 묶음과 전체 잔차 연결을 통과시킨다.
RDB 한 개는 앞선 특징을 연결하는 합성곱 5개와 잔차 계수 0.2를 사용한다.
RRDB는 RDB 3개와 바깥 잔차 연결로 구성한다. 활성화는 LeakyReLU 0.2이며,
끝에서는 2배 Nearest 확대와 합성곱을 두 번 거쳐 4배 RGB를 만든다.
구조 출처: [BasicSR RRDBNet](https://github.com/XPixelGroup/BasicSR/blob/master/basicsr/archs/rrdbnet_arch.py).

앱은 이 신경망을 C#으로 다시 작성하지 않는다. 검증된 NCNN `.param` 그래프와 `.bin` 가중치를
공식 `realesrgan-ncnn-vulkan.exe`로 실행한다. 파일 출처·크기·SHA-256은
빌드 기록의 의존성 목록에 고정되어 있으며 빌드 때 확인한다.
사진 모델의 두 파일은 조사한 Upscayl Standard 모델과 각각 동일한 SHA-256이었다.

```text
RGB PNG → x4plus / Vulkan 추론 → 4W × 4H RGB
→ 손상 검사 → 2× 요청이면 Lanczos 축소 → alpha 합성 → 저장

8× 요청: 2× 단계 결과(2W × 2H) → 다시 x4plus / Vulkan 추론 → 8W × 8H RGB
→ 손상 검사(2× 결과 기준) → alpha 합성 → 저장
```

사진의 질감·윤곽을 크게 보는 데 적합하지만, 학습한 패턴이 작은 글자나 로고의 형태를 바꿀 수 있다.
정확한 글자·수치·도형 복원이 필요하면 원본 보존 결과도 비교한다. 얼굴 전용 복원이나 생성형 프롬프트는 사용하지 않는다.

## 이미지 AI: Real-ESRGAN x4plus-anime 6B

공식 `RealESRGAN_x4plus_anime_6B`를 NCNN으로 제공한 `realesrgan-x4plus-anime` 모델을 사용한다.
RRDB 개수가 사진 모델의 23개에서 6개로 줄어든 구조이며 처리 배율은 동일하게 4배다.
가중치의 대상이 다르므로 단순히 사진 모델을 빠르게 실행하는 설정과는 구별된다.

```text
RGB PNG → x4plus-anime / Vulkan 추론 → 4W × 4H RGB
→ 사진 AI와 같은 손상 검사·배율 조정 → 원본 alpha 합성 → 저장
```

일러스트·아이콘·선화의 선과 색면을 확대하는 첫 선택이다. 조사한 Upscayl Digital Art의 `.bin`과
`.param`이 이 공식 모델 파일과 각각 같은 해시였다. Upscayl 앱/변형 엔진 소스를 배포 앱에 포함하지 않는다.

선의 굵기나 작은 모양도 추정에 따라 바뀔 수 있다. 픽셀 격자·정확한 로고 형태를 유지하려면
픽셀아트 또는 원본 보존을 선택한다. 모델 선택만으로 모든 입력의 품질을 보장하지 않는다.

### 두 AI 모드의 실행 설정

| 옵션 | 값 | 구현 의도 |
|---|---|---|
| 엔진 | 공식 NCNN Vulkan v0.2.0 | 포함된 로컬 엔진으로 추론 |
| `-s` | `4` | 모델의 기본 4배 출력 생성 |
| `-t` | `128` | 입력을 타일로 나눠 처리, 타일 경계 처리는 엔진 담당 |
| `-j` | `1:1:1` | 로드·처리·저장 병렬 수 제한 |
| `-f` | `png` | RGB 중간 결과 무손실 |
| TTA / 얼굴 보정 / DNI | 적용하지 않음 | 추가 추론·모델 혼합 없음 |

옵션 의미: [공식 NCNN 사용법](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan/blob/v0.2.0/README.md).
현재 UI에는 GPU 번호·타일 크기 선택을 노출하지 않으며 엔진 기본 GPU를 사용한다.
앱은 시작할 때 별도 프로세스에서 `vulkan-1.dll`로 인스턴스를 만들고 장치를 나열한다. 로더나 인스턴스가 없거나,
GPU 장치가 없거나 CPU용 Vulkan만 있으면 두 AI 모드를 막고 원본 보존으로 바꾼다. 저장 설정에는 원래 AI 모드를 남긴다.
확인이 시간 초과되거나 실행되지 않으면 AI 모드를 막지 않는다. 장치가 있어도 메모리 부족 등으로 추론이 실패할 수 있으며, 그 경우 위 실패 처리 규칙을 따른다.
오류나 취소 시 자식 프로세스 트리도 종료한다. 실패한 AI를 보간 결과로 바꿔 성공으로 표시하지 않는다.
모델 경로가 240자 이상이면 짧은 실행 경로를 안내한다.

## 원본 보존: 선형 색공간 Lanczos

학습 가중치 없이 주변 픽셀의 값을 보간한다. 먼저 RGB를 선형 광량 색공간으로 바꾸고
Magick.NET의 `FilterType.Lanczos`로 요청 크기를 계산한 뒤 sRGB로 되돌린다.
밝기가 비선형인 sRGB 값에서 바로 보간하는 경우와 다른 경계 밝기를 얻는다.

Lanczos는 sinc 기반 가중치를 가진 보간 필터다. 출력 위치 주변의 입력 값을 필터 가중치로 합산하며,
현재 앱은 필터 반경 등 세부값을 별도로 지정하지 않고 사용 중인 Magick.NET 기본값을 따른다.
날카로운 경계에서는 약한 링잉이 생길 수 있어 alpha에는 다른 필터를 사용한다.

```text
sRGB RGB → 선형 RGB → Lanczos 2× 또는 4× → sRGB → Triangle alpha 합성
8×: 위 2× 단계 결과에 같은 4× 단계를 한 번 더 적용
```

새 디테일을 추정하지 않는다는 의미의 이름이다. 원본 파일의 메타데이터·압축 방식·16bit/HDR 정밀도까지
그대로 보존하는 기능은 아니다. 출력은 공통으로 8bit sRGB이며 입력 파일 자체는 수정하지 않는다.

## 픽셀아트: Nearest neighbor

`FilterType.Point`로 가장 가까운 입력 픽셀을 고른다. 정수 배율 `s`에서 입력 한 칸이
`s × s` 출력 칸을 채우므로 픽셀 사이에 새로운 혼합색을 만들지 않는다.
8×도 2× 단계 뒤 4× 단계로 처리하며, 정수 배율의 Point 확대라서 결과는 바로 8×로 확대한 것과 같다.
alpha도 먼저 Point로 최종 크기에 맞춘 뒤 RGB에 복사한다.

```text
RGB → Point 정수 확대 ──┐
alpha → Point 정수 확대 ┴→ 합성 → PNG/WebP 무손실 저장 권장
```

GPU 없이 작동하며 도트의 계단·격자를 의도대로 유지한다. 사진에 적용하면 확대된 픽셀 칸이 보인다.
색공간 정규화, alpha 0의 숨은 RGB 정리, 손실 출력 형식 때문에 원본 파일 전체의 바이트 동일성을 의미하지 않는다.

## 투명 PNG와 가장자리 처리

alpha는 신경망에 넣지 않고 입력에서 추출한 값을 별도로 확대한다.

1. alpha가 0보다 큰 픽셀의 RGB는 유지한다.
2. 투명 픽셀의 검은 RGB가 경계 합성곱·보간에 섞이지 않도록 가시 픽셀 경계에서
   상하좌우 너비 우선 탐색으로 RGB를 최대 32픽셀 거리까지 전파한다. 가시 RGB는 덮어쓰지 않는다.
3. 색상 처리용 입력의 alpha를 255로 바꿔 RGB 확대를 수행한다.
4. 사진 AI·이미지 AI·원본 보존은 alpha를 Triangle로 확대한다. 픽셀아트는 Point로 확대한다.
5. `CopyAlpha`로 처리한 RGB에 합성한다. 완전히 투명한 출력 픽셀의 숨은 RGB는 인코딩 전에 정리한다.

이는 원본 투명 영역과 경계의 커버리지를 선택한 보간 규칙에 따라 유지한다는 뜻이다.
PNG 품질 회귀 검사는 4모드×3배율의 출력 alpha를 같은 규칙의 기준 이미지와 전 픽셀 비교한다.
다른 크기로 확대하므로 원본 alpha 배열과 출력 배열이 그대로 같다는 의미는 아니다.

## RGB 손상 감지

신고된 심한 RGB 격자 노이즈를 저장하기 전에 거르기 위한 휴리스틱이다.
두 AI 모드 모두 AI 단계마다 내부 4배 결과에 적용하며, 수치가 낮다고 이미지 품질이 우수하다는 평가는 하지 않는다.
8×의 두 번째 AI 단계는 원본 대신 2× 단계 결과에 원본 alpha를 입혀 기준으로 삼는다.

- `ColorError`: 원본과 AI 출력을 같은 작은 크기로 Triangle 조정한다. 너비는 최대 256,
  높이는 원본 비율에 따라 계산한다. 원본 alpha로 가중한 RGB 절대 오차 평균을 255로 정규화한다.
- `NeighborNoise`: AI 출력 중앙 최대 512×512 영역의 수평 이웃 RGB 차이 평균을 255로 정규화한다.
- 거부 조건: `ColorError > 0.28` 또는 `ColorError > 0.10 && NeighborNoise > 0.20`.
- 거부하면 결과를 저장하지 않고 다른 처리 방식을 안내한다.

이 기준은 심각한 색상·구조 손상 방어에 한정된다. 작은 글자의 오류·자연스러움·타일 경계 등 모든 문제를 검출하지 못하며,
강한 패턴에서 정상 결과를 거부할 가능성도 있다. fp16 또는 특정 GPU 하나를 손상 원인으로 확정하지 않았다.

## 저장·이름·처리 범위

| 항목 | 실제 동작 |
|---|---|
| PNG / WebP | 무손실 출력, alpha 지원 |
| JPG | 기본 품질 94, 투명 입력은 안내 후 중단 |
| AVIF | 기본 품질 94, speed 6, chroma 4:4:4, alpha 지원 |
| 파일 이름 | `원본이름-모드태그-배율x.확장자`, 충돌 시 `-2`, `-3` 순서 |
| 긴 파일 이름 | 파일 시스템의 255자 한도에 맞게 원본 이름 부분만 줄이고 모드 태그·배율·중복 번호 유지 |
| 픽셀 상한 | 입력 및 출력/중간 처리 각각 48,000,000픽셀 |
| 한 변 상한 | 출력/중간 처리 폭·높이 각각 32,768px, 실제 디코딩 후 재확인 |
| AI 입력 상한 | 내부 4배 처리 때문에 2×·4×는 최대 3,000,000픽셀, 8×는 최종 결과 기준 최대 750,000픽셀 |
| 비AI 입력 상한 | 요청 배율 `s`일 때 `입력 픽셀 × s² ≤ 48,000,000`, 8×는 최대 750,000픽셀 |
| 코덱 자원 제한 | 메모리 256MiB, 디스크 캐시 2GiB, 스레드 4, 폭/높이 32,768 |
| 자원 제한의 범위 | Magick.NET 설정이며 전체 앱/GPU 메모리 사용량의 상한은 아님 |
| 작업 경로 | 배포 EXE 옆 `bin/temp/job-…`; 개발 중에는 지정 F: temp |

권장 방식은 입력에 따라 달라진다. 이미지 AI로 아이콘을 먼저 확인하고 모양이 달라지면 원본 보존,
도트의 색·격자를 유지할 때는 픽셀아트를 사용한다. 사진 AI도 성공 메시지 뒤 전후 비교로 결과를 확인한다.
